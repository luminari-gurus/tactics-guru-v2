# Design

## Context

See proposal.md for issue, branch, base and acceptance identity. Merged #75 supplies pure RunState transitions; #76 supplies three ordered maps; #78 supplies atomic ownership/reward commands. #79 supplies RunSnapshot `{items, activeBattle}`, bounded codec, projected catalogs, guarded primary/backup storage, RunItemSession and mountRunItems. Those controls are currently fixture-only. BattleScene hardcodes the single-battle catalog/persistence and owns battle UI/presentation. BattleSession already accepts snapshots and invokes persistence after accepted commands, before presentation. replayBattle deliberately rejects noncanonical full-HP starts.

## Goals / Non-Goals

**Goals:** connect existing modules with one authoritative run state owner and a narrow scene-host boundary; preserve deterministic construction/replay, accepted-boundary saving and actual-control full-run evidence.

**Non-Goals:** parallel save models, generic scene/event/storage frameworks, serialized animation or full-run command history, root-route replacement, unrelated HUD/focus redesign, tuning encounters to make tests win, physical certification or deployment. #57's owner acceptance is sufficient for this baseline; record emulation limits and known findings without reinstating that gate.

## Decisions

1. **Additive `/run` entry.** Route `/run` through a small run bootstrap with a visible link from the current battle page and a return link. Keep `/`, `?scene=proof`, content-smoke and `/map` behavior. Start/Continue checks saved run state before writing; a new run must not silently overwrite damaged or incompatible slots. Preparation has an explicit Start encounter; reward claim returns to preparation. Outcomes show Start new run directly, matching #75. Mid-battle fresh-run intent uses explicit confirmation. Use scoped DOM screens with no active board inputs underneath. Alternative replacing `/` would disrupt accepted single-battle semantics and tests.
2. **Pure carried-party construction and replay.** Add runBattle helpers taking validated RunItems and immutable RunSaveContext. Use runBattleCatalog for equipment/spawn projection, createBattle for fresh initiative/flags/status/RNG, then apply only canonical living entry HP and validate the result. Keep the projected catalog fixed for that encounter. Add a fresh-from-validated-run-boundary BattleSession factory that records its initial state and commands; snapshot hydration remains a resumed continuation. Run replay independently reconstructs that exact run entry and rejects altered initial state before dispatching recorded commands. Leave replayBattle's strict original contract unchanged; do not treat arbitrary snapshot validation as proof of a canonical run start. Test replay tampering and resumed next-command equivalence.
3. **One controller owns RunSnapshot.** Extend RunItemSession's existing authority with encounter start, accepted battle update, terminal completion and new-run operations; retain its item/recovery API for mountRunItems. Bind active BattleSession callbacks to run ID, run/item revisions, encounter boundary and controller generation. Obtain terminal outcome/HP only from the owned session, never UI payloads. Before committing completion, derive transitionRun result and deterministic reward offer, validate the complete next RunItems/RunSnapshot, then publish once with activeBattle cleared. Terminal victory/defeat has no offer. Reward claim already advances run plus inventory atomically. No second mutable copy of party/ownership belongs to the scene. Alternative a second RunSession store would duplicate mutation and recovery logic.
4. **Reuse battle presentation through a small host interface.** Extract the hardcoded catalog/session/outcome/restart decisions at BattleScene's preparation boundary; default host preserves single-battle BattlePersistence. Run host supplies its projected catalog/session and handles accepted completion. Keep production HUD, BoardRenderer/Input, animation completion and BattleAudio. One BattleDialogs instance owns the active flow; reuse or transfer ownership only after disposing prior bindings. On terminal accepted command, persist the coherent run outcome immediately, but allow the final presentation to complete before switching screens. On reload, no old presentation is required. Generation guards and disposed sessions reject late callbacks. Preserve sound preference across in-page encounters/new-run and reset it on page load. Do not merge unaccepted #112/#113 changes.
5. **Reuse the #79 save format and recovery.** activeBattle owns live HP/RNG/actions; items.run.party remains encounter-entry HP. Save initial battle construction, every accepted player/enemy command, outcome, reward claim, item edit and fresh-run boundary. Validate snapshots with the same derived catalog on load and dispatch. Reconcile already-ended active snapshots on Continue idempotently. Keep run keys separate from single-battle/legacy keys. Preserve invalid bytes, exports, backups and nonfatal unsaved status. For explicit multi-slot reset, retain reviewed bytes in memory for export, compare before each removal, report partial failure honestly and keep current in-memory run/seed unchanged until reset succeeds; avoid presenting sequential deletes as a transaction. Do not bump the additive run format without an evidenced requirement. Pagehide must synchronously stop scene/controller callbacks; BFCache pageshow re-enters current-save startup before input or autosave. No cross-tab atomicity guarantee.
6. **Evidence from actual application controls.** Unit fixtures cover all survivor sets, equipment projection, invalid/stale boundaries and malformed snapshots. A deterministic pure simulation may discover a stable legal victory seed/policy, but browser evidence must start a fresh run and execute legal actions and reward/preparation choices through real controls for all three authored encounters. Retain per-encounter initial/commands/events, RNG and boundary snapshots; never inject terminal HP or advance scenes from test code. Defeat uses legal commands (for example Wait). Resume tests exercise battle/presentation, pending/claimed reward, preparation, final outcome, new-run and cached-history replacement. Explicit corruption/quota fixtures are failure tests, not full-run completion evidence.

## Risks / Trade-offs

- Legal full-run victory could reveal content difficulty → find legal deterministic policies without changing balance; report a demonstrated blocker and obtain scope approval before tuning.
- Scene cleanup can double-publish or leak input/audio → one controller, generation checks and tests for repeated callbacks, resize, page departure and replacement.
- Resume projection drift → immutable base catalog, derived catalog once per battle, canonical entry replay and exact RNG checks.
- Recovery partial reset → retain bytes, compare-before-remove, visible partial outcome; preserve live state until success.
- Unmerged HUD/focus work → minimal host seam, existing selectors where possible, explicit regression evidence; avoid unrelated repairs.
- Additional main-entry assets/code → lazy run entry and reuse existing art; measure build/transfer against base without claiming new hardware budget proof.

## Migration Plan

Additive route using existing run format/keys; no import, migration or automatic deletion. Existing single-battle and legacy saves remain untouched. A code revert removes the route but preserves run bytes for explicit recovery. No publishing, infrastructure mutation or production activation is included.
